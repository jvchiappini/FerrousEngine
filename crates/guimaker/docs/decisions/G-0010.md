# G-0010 - Popup present backend (swapchain vs layered)

## Context

Phase 8E measured a brand-new popup at +11-14 MB and 61-66 ms just in
`create_surface` + `configure`, plus 70-78 ms input-to-present. A hidden popup
kept about 50 MB of RSS, which is why the pool is capped at two. Every popup
was a normal `wgpu::Surface` with `PreMultiplied` alpha, even though a menu is a
small, short-lived, fully transparent window.

Phase 8F Lane B built a second backend behind `PopupPresent`:

- `Swapchain` is the historical path (a `wgpu::Surface` + swapchain);
- `Layered` creates no surface and no DXGI swapchain. It renders the popup's
  `GuiBatch` into an offscreen `Rgba/Bgra8UnormSrgb` texture on the shared
  device, reads it back with `crate::screenshot::capture_buffer`/`read_capture`,
  copies the premultiplied frame into a top-down 32bpp `CreateDIBSection` and
  calls `UpdateLayeredWindow` with `AC_SRC_OVER`/`AC_SRC_ALPHA`. The HDC, DIB
  and staging buffer persist across repaints.

`FERROUS_POPUP_PRESENT=swapchain|layered` overrides the default for the
experiment and for support. The cost evidence is
`crates/ferrous_engine/examples/p8e_popup_cost.rs`.

Measurements: release build, 320x200 popup, 800x600 main window, NVIDIA RTX
4050 Laptop, Windows 11, 5 runs (median and range), base `6f6a745` plus this
lane. `b` is the new-popup present setup step (surface + configure, or offscreen
texture + DIB); `new` is a brand-new popup through the public backend
(window/offscreen/renderer/first present); `pooled` is a hide + reopen of a
pooled window; `repaint` is one hover-colour change + one present on an open
window. RSS is the process working-set delta.

### Engine target (main renderer `Rgba16Float` + MSAA 4)

The engine's real UI target differs from the popup's 8-bit sRGB target, so the
first popup of either backend builds that pipeline variant once. The layered
run below reuses the variant the swapchain run already built, so its `b`/`new`
numbers are the steady-state ones.

main renderer afterwards; it is not specific to the layered path.

## Decision

The Windows default is `PopupPresent::Layered`
(`DEFAULT_POPUP_PRESENT` in `crates/ferrous_engine/src/windows.rs`). The
swapchain backend remains the fallback, is still selected on every non-Windows
host and on wasm32, and can be forced with
`FERROUS_POPUP_PRESENT=swapchain`.

Why:

- It removes `create_surface` + `configure`, the single largest first-popup
  cost: the present setup drops from 36-75 ms to 0.075-0.235 ms and from
  11-13 MB to 0.004-0.008 MB.
- A brand-new popup falls from 52.6-69.2 ms to 8.5-9.6 ms and from about 11 MB
  of RSS to about 0.52 MB. That is the memory the pool existed to hide.
- A pooled reopen is at parity (2.9-3.7 ms both paths).
- A repaint after a hover change is 0.30-0.41 ms, not worse than the best
  swapchain result (0.28 ms on Vulkan) and far below it on DX12 (6.95 ms, where
  `Fifo` blocks on the vblank).
- The layered target uses `Bgra8UnormSrgb`/1-sample, the same variant a popup
  surface usually chooses, so a process that has opened one popup of either
  backend shares the cached pipelines of the other.

The decision changes if any of these stop holding:

- Popup size grows far beyond menu/tooltip sizes. The DIB upload and readback
  are O(pixels) and CPU-bound; at 320x200 they are under 0.5 ms, a full-window
  overlay would not be.
- A required effect needs the GPU-composited path (for example a popup that
  must sample the main window's HDR target or use a hardware overlay plane).
- A host rejects `UpdateLayeredWindow` (some remote-desktop/emulation
  configurations). That is what `FERROUS_POPUP_PRESENT` is for.
- The first-popup pipeline variant compile becomes the dominant cost. Then the
  right fix is prewarming the sRGB/1 variant at startup, not reverting the
  present backend.

## Consequences

- `PopupPresent` is public in `ferrous_engine::windows`, with `parse`,
  `from_env`, `resolved` and `label`. `WinitPopups::new` reads
  `FERROUS_POPUP_PRESENT`; `WinitPopups::with_present` is the explicit
  constructor the cost example uses.
- The layered popup registers `popup:{handle}:offscreen` instead of
  `popup:{handle}:swapchain` in `memory-report`; the registry is switched by
  `register_popup_present`, and a resize re-registers the new size.
- `PopupWindow.surface` is an `Option`; the layered path also carries an
  `OffscreenTarget` and a Win32 `LayeredSurface`. The surface/DIB drop before
  the window they belong to.
- The per-popup screenshot capture keeps working on both backends: the
  swapchain copies its acquired image, the layered path returns the RGBA frame
  it already read back for the DIB. The `p8d_popup` main-window composer runs
  unchanged and its evidence capture still reports `on_popup_screenshot`.
- Resize drops and recreates the offscreen target and the DIB; move calls
  `UpdateLayeredWindow` with the existing DIB; hide/show, minimize/restore,
  per-popup DPI, the work-area clamp, `WS_EX_NOACTIVATE`, the pool cap and the
  routing map are unchanged.

Known deviations, recorded rather than hidden:

- `UpdateLayeredWindow` requires premultiplied BGRA. The GUI pass blends
  straight-alpha over a transparent clear, so the framebuffer bytes are
  premultiplied already; the layered path only swaps R/B. The target is sRGB,
  so for semi-transparent AA fringes the premultiplication is the sRGB-encoded
  one, not a linear-space premultiply.
- winit rewrites `GWL_EXSTYLE` from its own tracked flags on a visibility
  change, which drops `WS_EX_LAYERED`. The backend re-asserts the bit before
  every `UpdateLayeredWindow`; it is one read/write on an already-set bit.
- The layered path reads the whole frame back synchronously
  (`device.poll(Maintain::Wait)` in `read_capture`) and copies it into the DIB;
  that is the 0.30-0.41 ms repaint. The swapchain path does neither.
- The layered path has no vsync. For a menu shown in response to input this is
  desirable; a continuously animated popup would tear and should use the
  swapchain backend.

## Alternatives rejected

- **Keep the swapchain default.** Rejected: it pays 36-75 ms and 11-13 MB for
  a surface a menu does not need, and keeps about 50 MB per pooled popup.
- **Use a DXGI composition swapchain / DirectComposition visual.** A larger
  change than this phase needs, and it still allocates a swapchain per popup.
  The layered path is the smaller experiment that removes the measured cost.
- **Render with GDI only (no GPU).** Rejected: the popup must paint the same
  `GuiBatch` (text, SVG, rounded clips) as the main window, and a CPU
  rasterizer would be a second renderer to keep correct.
- **Force Vulkan for popups because its swapchain repaint was fastest.** The
  repaint difference (0.28 vs 0.41 ms) is an order of magnitude smaller than
  the first-popup difference, and the backend choice is the application's, not
  the popup's.

# G-0004 — Grapheme segmentation for the text editor

## Context

Phase 4's `TextEditor` must delete and move by grapheme cluster, not by
`char`: one backspace has to remove a whole emoji (`👩‍👩‍👧‍👦`), a flag
pair (`ðŸ‡¦ðŸ‡·`), a skin-tone modifier or a base letter with its combining
accent. Rust's `char` is a Unicode scalar value, so a naive implementation
leaves broken bytes or splits a cluster in half. Word movement and
double-click selection need the same class of boundary data.

Writing a correct extended-grapheme-cluster segmenter means implementing
Unicode Standard Annex #29: the combining-mark tables, the ZWJ rules, the
regional-indicator pairs and the prepend/spacing-mark classes, plus keeping
the tables current. That is a large amount of table data and a subtle
specification, and it is not the part of the library that makes GUIMaker
different.

## Decision

Use `unicode-segmentation` 1.13 (MIT/Apache-2.0) inside `guimaker` and wrap it
in `guimaker::input::grapheme`, which exposes byte-index helpers:
`previous`/`next`, `boundaries`, `count`, `previous_word`/`next_word`,
`word_at`, `line_at` and `line_starts`. The rest of the library never imports
the dependency directly, so a future replacement (or a `ferrous_text` crate)
is one module away.

Why this crate:

- it is already in the workspace lock file through another dependency, so the
  addition costs no new transitive tree and no new licence review (both MIT
  and Apache-2.0 are already accepted by the workspace);
- it implements UAX #29 including ZWJ emoji and regional indicators, which is
  exactly the set the tests exercise;
- it is small, pure Rust and has no runtime state, so the editor stays
  deterministic and headless.

The wrapper rounds byte offsets down to a cluster when a caller passes an
offset inside one, so no public method can split a cluster even if a host
indexes by `char`.

## Consequences

- `guimaker` gains one normal dependency (`unicode-segmentation = "1.13"`).
  It is GPU-free and windowing-free, so the core stays headless and the
  boundary check is unchanged.
- Caret arithmetic is `O(clusters)` in the prefix it covers. The editor
  caches line byte ranges and widths; a keystroke does not re-segment the
  whole document.
- The dependency is allowed only in `input::grapheme` and `text_editor`
  (the worker of the two). A grep for the crate name outside those files is
  a review failure.
- `guimaker_ferrous` maps the same clusters onto `ferrous_font` shaping in
  phase 5; the two must agree on what a caret can sit between.

## Alternatives rejected

- **Implement UAX #29 ourselves.** Rejected: the tables are large, the ZWJ
  and regional-indicator rules are easy to get wrong, and correctness would
  be our maintenance burden for no product benefit. The wrapper keeps the
  door open to a later in-house crate with the same interface.
- **Segment by `char` and accept broken emoji.** Rejected: the prompt
  requires grapheme-correct deletion and the failure is visible (a backspace
  that leaves half a family emoji).
- **Add `unicode-width` for caret columns.** Not needed: caret x comes from
  `TextMetrics::advance`, which the host implements with real font advances.
  Width tables would be a second source of truth.

# G-0001 — GUIMaker library architecture

## Context

Motioner's chrome is hand-written: `crates/motioner_ui/src/start.rs` is 973
lines with 28 `Rect::new` call sites and 94 numeric `.px(...)` arguments
(`start.rs:418-516`, `571-756`, `758-827`, `869-898`), and the same geometry
is encoded four times (`StartLayout::compute`, `draw_home`, `draw_dialog`,
`text_field`). Colours are mutated per call (`start.rs:537`, `661`, `768`,
`775`), hover states are five hand-written branches plus a private
`ButtonKind` that duplicates `widgets.rs:32`, and hit testing re-derives
rects that `layout.rs` already owns (`app/pointer.rs:333-340`, `396` against
`layout.rs:1280-1281`, `891-901`). A screen written that way is a stack of
arithmetic, and no model can keep it aligned.

The engine's own UI stack does not solve it either. `Style` carries layout
only — margin, padding, size, alignment, display, position, overflow, gap
(`ferrous_ui_core/src/primitives.rs:262-273`) — so colour, radius, border,
shadow and type roles live inside each widget (`theme.rs:118-156` is a flat
12-colour palette). Widgets are `Box<dyn Widget<App>>` that mutate the app
from callbacks (`context.rs:19-33`; `button.rs:48-57`, `slider.rs:12`,
`checkbox.rs:10`), the JSON loader stores absolute pixels
(`fui_loader.rs:11-17`, `56-63`), and text is measured with 8 px-per-char
guesses (`button.rs:239-243`, `label.rs:87-95`, `text_input.rs:131`) because
the UI core cannot reach `ferrous_font`, which is a `wgpu` crate
(`ferrous_font/Cargo.toml:9`).

What the engine does have is the draw side and it works: `GuiBatch` with
quads, per-corner radii, border, one soft shadow, gradients, textures,
scissor clips and layers (`ferrous_ui_render/src/gui_batch.rs:15-35`;
`gpu_types.rs:28-40`); retained batch ranges (`gui_batch.rs:56-64`,
`216-242`, `716-801`); MSDF text with kerning and GPOS
(`ferrous_font/src/layout.rs:1225-1346`, `791-798`); damage targets and
presenters from prompt 18 P5/P7 (`persist.rs:116-126`,
`ui_present.rs:224-279`); and the redraw scheduler (`redraw.rs`). Motioner's
own seeds are good too: the semantic token table and WCAG test
(`theme.rs:126-229`, `50-61`), single sRGB→linear conversion
(`theme.rs:32-46`), 4 px grid with DPI rounding (`theme.rs:251-328`),
kerning/ellipsis/baseline text (`text.rs:121-208`), the 16-unit vector icon
grid (`icons.rs:196-228`), and the pure character-indexed `TextEdit`
(`text_edit.rs:1-217`).

D-0004 named "Ferrous UI and GUIMaker" as the editor's destination, D-0018
banned the `guimaker` prefix, D-0020 deferred the integration and D-0021
built an immediate painter instead. Prompt 15 moves GUIMaker into this
workspace and gives it the controllers, while the engine keeps the draw
calls. This decision fixes the shape of that library before any of it is
written.

## Decision

### 1. Crates, inside this workspace

| Crate | Package | Contains | May depend on |
|---|---|---|---|
| `crates/guimaker` | `guimaker` | design tokens and themes, view tree, style, layout, input routing and controllers (hit testing, hover/press/focus, scroll, gestures, text editing), state store, display list, lint, inspect | `taffy`, `glam`, `serde`/`ron`, `ferrous_events`; nothing that draws |
| `crates/guimaker_ferrous` | `guimaker_ferrous` | display list → `GuiBatch`; `TextSystem` over `ferrous_font`; textures, glyphs, icons; the `FerrousApp` host adapter | the `guimaker` core plus `ferrous_ui_render`, `ferrous_font`, `ferrous_2d`, `ferrous_gpu`, `ferrous_render_graph`, `ferrous_renderer`, `ferrous_svg`, and the GPU-free foundation |
| `crates/guimaker_gallery` | `guimaker_gallery` | storybook binary, screenshot CLI, bench harness | both |
| `crates/guimaker_designer` | `guimaker_designer` | the revived designer (phase 11) | both |

`scripts/check_boundaries.py` encodes exactly this table and fails the gate
on any other edge, in either direction, including dev- and build-dependencies
and renamed dependencies. No engine crate may depend on a `guimaker*` crate,
so a Ferrous project that does not use GUIMaker compiles none of it.

Paths are workspace path dependencies. Motioner will take `guimaker` and
`guimaker_ferrous` through its existing `engine/ferrous` submodule during
phase 10, so one engine copy is built by construction: no `[patch]`, no
second submodule.

Docs live in `crates/guimaker/docs/` with their own `mkdocs.yml` section
(`build_docs.sh:16-37` copies them to `docs/guimaker/`), decisions in
`crates/guimaker/docs/decisions/`.

### 2. Programming model: a declarative tree rebuilt on change

The app builds a view tree from its state; GUIMaker lays it out, routes this
frame's input through it and emits a flat display list.

- **Rebuild is event-driven, never continuous.** The tree is rebuilt when
  input arrives, when the app marks state changed, when an animation is
  running, or when a worker marks a region dirty. A still window rebuilds
  nothing and renders nothing.
- **The tree lives in an arena**: a flat `Vec<Node>` plus `NodeId` indices,
  reset (not freed) between builds, with text stored as borrowed or interned
  slices. Steady-state rebuilds allocate nothing.
- **Layout** runs on `taffy` 0.7.7 — the same version and the same solver the
  engine uses (`ferrous_layout/Cargo.toml:7`, `Cargo.lock` `taffy 0.7.7`),
  reached by GUIMaker's own dependency, not through `ferrous_layout`, which
  depends on `ferrous_ui_core`. Unchanged subtrees are memoised by a hash of
  style + content + available size; the last rect of every node is kept and
  compared bit-exactly so a rebuild that produces the same layout produces
  no damage and no layout work.
- **Input is routed through this frame's tree**, after layout and before
  paint: no one-frame lag, no retained widget objects to go stale.
- **Persistent state lives in a store keyed by a stable id path**:
  explicit `.key(...)` on list items, derived paths elsewhere. Hover, press,
  focus, scroll offsets, text-edit cursors, open popovers and transition
  progress live there, so a rebuild cannot lose them and a list reorder
  cannot transfer a hover to a different row.
- **Interaction returns typed messages**: the tree is built with
  `Ui<Msg>`, and the frame returns `Vec<Msg>` (Elm style). No
  `Rc<RefCell>`, no callbacks that capture app state. Motioner's
  `StartAction`/`Command` map onto messages one to one.
- **One frame is a pure function** of (view, store, theme, viewport size,
  scale, clock): build → layout → route → display list → damage. The clock is
  injected; `Instant::now()` is never read inside the library, so the same
  inputs give a byte-identical display list and therefore a byte-identical
  screenshot.

Why this model: it is the cheapest to write correctly and the only one that
cannot hold stale widget state; a model (or a person) describes structure,
and the numbers stay out of the source. It meets the budget table because
the expensive parts are cached — layout is memoised, the tree is an arena,
routing is an index lookup, and nothing runs when nothing changes.

The condition that would change it is recorded rather than hidden: if
build + layout + routing + command list for the start-screen recipe exceeds
0.3 ms CPU per frame after memoisation (phase 9B), the fallback is a retained
tree keyed by id path with per-node dirty flags. The public API does not
change either way; only the internals do.

### 3. Text: a trait in the core, a real implementation in the adapter

```text
trait TextSystem {
    fn shape(&mut self, text: &str, style: &TextStyle, max_width: Option<f32>) -> TextShape;
}
```

`TextShape` carries per-line boxes, per-glyph advances, the shaped width and
height for layout, and the caret positions derived from the same data. The
core never rasterises, never touches a glyph atlas and never sees a font
file; it only asks for metrics. `guimaker_ferrous` implements the trait over
`ferrous_font` (kerning, GPOS, ellipsis at layout time) and Motioner's
`text.rs` becomes its starting point, not a second copy.

Headless tests use a `FakeTextSystem` that reads a **committed metrics table
generated from the real Inter files** by a `guimaker_ferrous` example
(`cargo run -p guimaker_ferrous --example dump_metrics`). It is a table of
real advances, not a mock of rendering: layout tests are deterministic,
GPU-free and still reflect the font a user sees.

### 4. Display list: engine-agnostic, one adapter

The core's output is a flat, ordered list of draw commands: rounded rect
with four radii, border, soft shadow, linear/radial gradient, image with
`fit` (`Cover`/`Contain`/`Fill`), text run, icon or vector path, clip
push/pop with radius, layer opacity, backdrop-blur request. It names no
engine type. `guimaker_ferrous` maps each command onto `GuiBatch`
(`rect_radii`, `border`, `shadow`, `image`, `push_text`, `push_icon`,
`push_svg`, `push_clip`/`pop_clip`, `begin_layer`), and if a command has no
honest mapping, the capability is added to the engine as a generic feature
and documented here — the adapter never grows drawing logic.

Known engine gaps to confirm in phase 5, from the audit: scissor clips are
rectangular only (`gui_batch.rs:1188-1199`) so rounded clips are missing;
one shadow per quad (`gui.wgsl` bit 7) so elevation-2 pairs need two quads
or a shader change; no backdrop blur; no gradient border; the SVG path is a
stub (`ferrous_svg/src/lib.rs:64-123`). Each becomes a generic engine
feature with docs and a documented fallback until the pin moves.

### 5. Theming boundary and colour space

`guimaker::theme` is the only module with literal design values. Spacing,
type roles, radii, elevation, borders, motion, colour roles and density are
tokens; styling takes tokens (`pad(S4)`, `radius(Md)`, `text(Body)`,
`Tone::Muted`), and the pixel escape hatch is explicit (`Px(13.0)`) and
reported by the design lint. One `Color` type with constructors that name
their space (`Color::srgb`, `Color::linear`, `Color::oklch`) makes the
D-0021 double-encoding bug unrepresentable; conversion happens once, inside
the type. Themes are data (format decided in phase 1) so an app ships a
theme file and the designer edits one; built-ins are dark, light and
high-contrast. Motioner's D-0021 seeds and its WCAG test move here in
phase 1; `theme.rs` keeps only what is Motioner-specific.

### 6. Controllers come here; drawing stays there

Per the ownership split, these move from the engine into `guimaker` and the
engine copies are deleted in the same change, so one implementation is left:

| Moved | Source | Lands |
|---|---|---|
| spatial index (grid/BVH over laid-out rects) | `ferrous_ui_core/src/spatial_index.rs:1-379` | phase 2 (with layout) |
| incremental layout: dirty flags, rect diffing, damage | `ferrous_ui_core/src/ui_tree.rs:39-83`, `160-172`, `278-390`, `510-588` plus the taffy sync in `ferrous_layout/src/lib.rs:57-324` | phase 2 |
| scroll controllers (wheel, inertia, scrollbars, scroll-into-view) | `ferrous_ui_core/src/widgets/scroll_view.rs:1-145`, `widgets/virtual_list.rs:1-309` scroll half | phase 4 |
| virtual list / tree view logic | `widgets/virtual_list.rs:1-309`, `widgets/tree_view.rs:1-527`, `widgets/virtual_grid.rs`, `widgets/data_table.rs` | phase 4 |
| event routing, hover/press, `EventManager`, hit test | `ferrous_events/src/lib.rs:15-82` (and with it the `ferrous_ui_core` edge that crate carries) | phase 4 |
| text editing | Motioner `text_edit.rs:1-217` | phase 4 |

The move lands with the crate that can hold it: phase 2 for layout and the
index, phase 4 for the controllers that need the gesture state machine.
Performance is proved with the prompt 18 benches and `scripts/perf_bench.py`
before and after each move; a regression over 10 % blocks the phase.

`ferrous_events` becomes the raw platform vocabulary (pointer, keys, wheel,
IME, clipboard, file drop, modifier state, platform double-click time and
distance, injected clock) with no UI-core dependency; the `guimaker` core
depends on it and on `ferrous_core` (default features, GPU-free),
`serde`/`ron`, `glam` and `taffy` — nothing else.

Everything that stays: `GuiBatch` and its retained ranges,
`ferrous_ui_render` in full, glyph atlas and rasterisation, offscreen
readback for screenshots, the damage/present targets, the redraw scheduler,
and scene/canvas picking (phase 4B, engine-side).

### 7. Damage is GUIMaker's output; the offscreen present is its consumer

Every frame returns `damage: Vec<Rect>` — the union of nodes whose paint
changed, from the rect diffing above. The adapter hands those rects to the
engine's damage path. Prompt 18 P7 left `UiPresenter` off because a
whole-frame copy loses 31.8 % on scrub and 66.8 % on hover; the number that
would make it win is a **scissored** repaint of the damaged rects, and that
is only possible once somebody computes trustworthy damage. Phase 5 emits
per-node damage; phase 9B enables the scissored persistent repaint and
measures it against the P7 baselines. Until then, full repaint stays the
default and nothing regresses.

### 8. No wrapping of `ferrous_ui_core`

GUIMaker does not implement or wrap the `Widget` trait, does not use
`UiSystem`, `RenderCollector` or `fui_loader`, and is not built on
`ferrous_ui_core` widgets. What it reuses is the draw side listed in §4 and
the font stack in §3. Deprecation candidates, recorded as an engine backlog
note and not done here: the 23 `ferrous_ui_core` widgets, `ferrous_gui`'s
`UiSystem` (`system.rs:20`), `fui_loader`'s absolute-pixel format, and —
once nothing in the engine uses it — `ferrous_layout` itself. `ferrous_svg`
must be decided in phase 5 (real parser, or delete and use vector paths).

### 9. New dependencies

`taffy 0.7.7` (MIT), already in `Cargo.lock` through `ferrous_layout`:
writing a correct flex + grid solver is a multi-month detour and a second
solver would disagree with the engine's; transitive deps `arrayvec`, `grid`,
`serde`, `slotmap` are small and already present. `serde` + `ron` for theme
files (already workspace dependencies of `ferrous_ui_core`). Nothing else is
added without a decision: `unicode-segmentation` (phase 4) is the next
expected one.

## Consequences

- One repository, one `target`, one gate for the engine and its UI library;
  the boundary check makes "optional UI" enforceable instead of aspirational.
- Motioner's migration in phase 10 is a dependency change plus a theme
  built from its D-0021 seeds, not a second UI stack. D-0004, D-0018,
  D-0020 and D-0021 are amended there, with numbers.
- The core stays testable headless and deterministic: no GPU, no window, no
  clock reads, no font files. Layout snapshots, hit tests, text-clamp and
  lint output are all plain data.
- Rebuilding on change means every widget must be expressible as a pure
  function of state and store; a retained-only pattern (a widget that
  mutates itself) is not addable later without reopening this decision.
- The prompt 18 performance policy keeps applying: the same instruments,
  the same budget table, three-run medians, and a regression over 10 %
  blocks a phase.
- Debug data sources are designed now, for prompt 19: every node has a
  stable id and path, layout rect, resolved tokens, cache state and repaint
  reason, and the commands it produced are attributed to it. Prompt 19 only
  adds the panels.

## Alternatives rejected

- **Wrap `ferrous_ui_core` widgets behind a nicer builder.** The blockers
  are inside the widgets (state in callbacks, hard-coded colours, guessed
  text metrics), so a wrapper inherits them and the double implementation
  stays.
- **A retained tree keyed by id, mutated in place.** Cheap in theory, but
  every state change must find and patch nodes, stale-state bugs are the
  norm, and a model writing a screen has to reason about mutation. Kept as
  the measured fallback in §2 instead.
- **Immediate-mode painter with a token module (D-0021 extended).** That is
  today's Motioner: tokens exist and the screens still hand-place everything.
  Without layout and controllers in the library the arithmetic returns.
- **An external toolkit (egui, iced, Slint, a web view).** Rejected by
  D-0004, by the boundary check, and by the project's reason to exist: one
  engine, one drawing path, no second renderer.
- **A separate GUIMaker repository, pinned like the engine.** Two
  repositories, two targets and two gates for something that cannot work
  without the engine's `GuiBatch`; the old repository is retired
  (`github.com/jvchiappini/GUIMaker`, `9dcbc28`).
- **Emitting absolute positions, like the old designer.** Codegen writes
  GUIMaker builder code with tokens and structure; a rectangle in generated
  code is a bug in the generator.

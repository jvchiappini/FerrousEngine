# G-0003 — Theme file format

## Context

Themes must be data: an app ships a theme file, and a designer edits that file
without rebuilding the app. G-0001 §5 puts the literal design values in
`guimaker::theme` and says themes are data whose format is decided in phase 1.
G-0001 §9 lists `serde` + `ron` as the expected dependencies, and both are
already in `Cargo.lock` through `ferrous_ui_core`.

The format has to express Rust enums, nested structs, arrays of structs and
comments, because a theme holds things like `Density::Compact`, `Radius::Md`
and a list of shadow layers a person will read and change by hand.

## Decision

Use **RON**, `ron = "0.8"` (already in `Cargo.lock`), serialized with
`PrettyConfig` and round-tripped by serde. `Theme` derives `Serialize` and
`Deserialize`. `Color` serializes as `#RRGGBB` or `#RRGGBBAA`.

Why RON: it expresses Rust enums (`Density::Compact`, `Radius::Md`), comments
and nested structs with no schema layer between the file and the type. TOML
cannot represent enum variants or arrays of structs cleanly, and JSON has no
comments and is noisier for a hand-edited design file.

## Consequences

- Theme files are named `*.theme.ron`.
- A designer edits them directly; no export step and no parallel schema.
- The round-trip test pins that a loaded theme re-serialises to the same
  canonical file. Colours travel as 8-bit hex, so the round-trip is idempotent
  at the file level rather than bit-identical in floating point.
- No new dependency: `ron` 0.8 is already in the lock.

## Alternatives rejected

- **TOML.** Cannot express enum variants or arrays of structs cleanly, and
  would need a parallel schema layer to map them.
- **JSON.** No comments, and the punctuation makes a hand-edited design file
  hard to read.
- **A binary format.** Not editable by a person, which defeats the reason
  themes are data at all.

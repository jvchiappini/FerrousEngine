# G-0005: OS font lookup without a font-database crate

- Status: accepted
- Date: 2026-11-23

## Context

Phase 8B adds a fallback chain to text shaping. After the primary face and the
theme's fallback families, a character the UI does not ship (CJK, Arabic,
symbols, emoji) has to be found in the operating system's fonts. The prompt
allows an OS API (DirectWrite/CoreText/fontconfig) or a font-database crate, with
a decision record covering the crate's size and licence.

## Options

1. **`fontdb`** (MIT/Apache-2.0, ~0.5 MB source, pulls `ttf-parser` and
   `memmap2`): enumerates every face, parses the `name` table and exposes
   `has_char` per face. It would add two dependencies to `ferrous_font`, which
   today has `anyhow`, `log`, `rustc-hash`, `wgpu` (desktop: `rayon`), and it
   would still hand us bytes that the existing `FontParser` has to parse again.
2. **DirectWrite** (`windows` crate with `Win32_Graphics_DirectWrite`): the
   authoritative Windows answer, but it means a platform-specific dependency and
   a COM binding for a feature whose first consumer only needs "which `.ttf`
   covers this code point".
3. **In-house directory scan** (`ferrous_font::system`): enumerate
   `%WINDIR%\Fonts`, read each file, and use the parser the crate already has
   (`FontParser::has_glyf` + `get_glyph_index`) to test coverage. No new
   dependency, no new licence, and the same parser that will read the face
   afterwards does the test.

## Decision

Option 3. The scan costs one `read_dir` per directory, cached for the process,
and reads files only until every missing character is covered. It runs lazily,
on the first character the primary and theme faces do not cover, so cold start
opens nothing. The limitation is explicit: only `glyf` outlines are found —
CFF/OTF-outline and collection (`.ttc`) faces are skipped, and the caller falls
through to the next candidate. On this reference machine that is enough: Arial
Unicode covers CJK + Arabic + the check mark, and Segoe UI Symbol covers the
film emoji, all as `glyf`.

If a future platform (Linux font trees with only CFF faces, or colour emoji)
needs more, the decision is to add `fontdb` then — recorded here so the
reversal has a baseline: +2 dependencies, MIT/Apache-2.0, and the scan code
above is deleted.

## Consequences

- No new crate, no licence surface, no lockfile churn.
- `system::find_for` is the only OS-aware code; it has its own tests and is
  skipped gracefully on a host without system fonts.
- Colour emoji (COLR/CBDT) is **not** solved by this: a bitmap/vector colour
  glyph needs an RGBA atlas page and a second text pipeline, which this phase
  does not deliver.
